# ADR-0038：GMS更新雷达的扫描、比较和通知

- 状态：已采纳（Accepted）
- 关联：ADR 0002、0004、0010、0015

## 背景

常用工具中的 GMS 要求、包、Mainline 包、测试套件、Critical_Patch 和
Mainline 豁免已有人工扫描入口及两个领域数据库，但没有统一的每日计划、
监听范围快照、扫描前后差异及可追踪的汇总邮件。直接定时刷新页面依赖浏览器，
而不完整扫描可能将缺页误认为数据移除。

## 决策

1. 在 `features/system/update_radar/` 实现 Controller 侧服务，使用 SQLite
   持久化计划、每轮配置快照、扫描结果和字段差异。计划默认关闭；默认时间为
   Asia/Shanghai 每日 04:00，默认仅对变更或扫描失败发送邮件。
2. 六项任务可全选或按需选择。将选择映射为现有扫描器的数据源并去重；
   GMS 下载源同时提供的包/套件信息可以刷新，但雷达只记录所选类别的变化。
   运行中的任务选择冻结，不随后续配置编辑改变。
3. 生命周期由 Controller 进程锁覆盖的应用启动/停止管理。SQLite
   `BEGIN IMMEDIATE` 下原子认领任务、推进下次计划，并保存唯一计划时点，
   防止重复触发。恢复时补跑一个错过的计划，不重放全部历史时点。
4. 现有 CLI 经 `foundation.processes.run_local_command` 的 argv 边界执行，
   显式指定临时数据库，禁用无人值守自动打开登录浏览器。先备份领域数据再
   全量扫描；只有返回成功且扫描覆盖完整的组才发布。缺页及失败组保留原值。
   复用两个人工扫描 API 的互斥状态，避免平台内人工和计划扫描相互覆盖。
5. 以各表业务主键比较结构化记录，剔除扫描时间、行 ID、内容哈希等元数据。
   保留新增、修改、移除的完整前后字段值，并保留本次失败覆盖缺口。
6. 邮件复用 `features.email` 公共发送服务、全局 SMTP 与 outbox 台账；
   采用纯文本，外部页面内容只作为证据。扫描结果先持久化，再发送汇总，
   发信失败与扫描状态独立。明确未知投递状态不自动重发；管理员可核对后
   用当前邮件配置重发原批次汇总。
7. 设置弹框的 HTML、脚本和样式在工具卡片及独立雷达页面共用；各文档仍由
   既有 ModalManager 或 EmbeddedModalController 独占模态生命周期。
   页面初始化只读取配置，保存、扫描和重发均由用户操作触发。

## 影响与边界

- 计划依赖平台服务运行；浏览器无需保持打开。首次建立基线会记录新增。
- 需要既有 Partner 登录状态和可用 SMTP；失败必须可见，不能作无变化结论。
- GMS 与 Mainline 豁免为两个发布组，允许一组成功而另一组失败并记录部分结果。
  不提供跨领域数据库与雷达账本的分布式事务。进程在发布与记账之间崩溃时，
  该轮标记中断，不能声称完整比较已完成。
- 不保证 SMTP 恰好一次投递；持久化发送中状态和独立 outbox 用于人工核对。
- HTTP 配置、手动触发和发信仅管理员可操作，已登录用户可查看共享扫描结果；
  收件人配置不向普通查看者暴露。
