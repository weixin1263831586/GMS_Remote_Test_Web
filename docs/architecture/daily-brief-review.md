## 主要修复

| 问题 | 本轮处理 |
| --- | --- |
| 并发 start_run / refresh 返回不存在的 run_id | 使用事务返回的 job 所属 run_id，并返回同一 job_id 和持久化状态；双 Repository 并发测试覆盖 manual/delta |
| 单条重分析可能执行到同日最新 run | Worker 全程携带入队时的 run_id，服务检查 owner；测试覆盖同一天存在更晚的 run |
| Prompt 与实际必填字段不一致 | `daily_brief_result.IssueResult` 同时生成 Prompt JSON Schema 并验证返回值，包括嵌套证据、动作和相似工单 |
| 用 confirmed/likely 补出高置信度 | 删除枚举推算，只接受显式数值；缺失值触发有限次数的 Schema 修复；界面注明“模型自评” |
| 超时天数无限加分、无附件减分 | 优先级限制在 0–100，7 天后额外年龄分最多 5；取消附件对业务优先级的影响 |
| 每个工单都强制深度诊断 | 批量晨报使用 triage：读取工单、journals 和相关附件，输出短待办；不要求历史/源码检索、不允许确定性根因；单条按钮执行深度诊断 |
| 汇总报告堆叠全部长文 | 汇总保留摘要和建议，长报告留在工单详情；UI 直接展示下一步，按规则分排序，不再只显示前 10 项 |
| “超 03 天未回复” | 改为直接格式化数量并增加零值回归 |
| 附件列表成功被显示为附件已检查 | 附件内容检查读取持久化 Evidence Gate；缺失旧 gate 时不冒充已检查 |
| 生成插件权限只能增加、不能撤销 | 同步工具按文件类别双向恢复 0644/0755，内容相同也校正权限；生成树由脚本更新 |
| 分类名插入 innerHTML | 使用 option.value / textContent，新增恶意分类名及重复刷新浏览器回归 |
| 重分析冲突统一返回 404 | 运行中的工单返回 ApiError 的 STATE_CONFLICT / 409；不存在仍为 NOT_FOUND / 404 |
| 本地“存为案例”错误引用普通 Redmine repository | 改用 owner 的 DailyBriefRepository；UI 携带 run_id；增加正确保存、跨 owner 拒绝和 Agent 写入拒绝测试 |
| 混合已预约与空闲设备时租约不完整 | 集群操作为全部目标生成 fencing token，只释放新申请的 claim；不借用另一并发操作的临时 claim |
| 用户管理状态卡片失效 | 状态卡片原先依赖已删除的下拉框；改为页面状态管理，删除失效的搜索框引用，刷新后保留筛选 |
| 文件体积门禁和重复定义 | 拆分晨报创建流程、结果契约、源码 provider 协议/索引实现和测试夹具；删除重复 JOB_KINDS 和未使用常量，不提高体积预算 |

## 采用范围与保留限制

1. 采用 ADR 0008 的渐进方案：保留现有结果字段和旧报告展示兼容性，在执行
   模式上分离 triage / diagnosis。回复草稿按是否需要回复生成，未另建独立
   Reply Assistant 产品或接口。
2. 晨报数据仍来自待回复/超时未回复集合。没有凭现有数据虚构全量新增、
   关闭、等待外部等工作状态；UI 已注明“待回复事项”。
3. 取证调用完成和自然语言结论得到证明是不同概念。本轮没有声称已实现
   全句级证据绑定，也没有人为添加未经校准的 evidence_confidence 数字。
4. OpenGrok 是动态索引，未固定 commit 的结果不能当作可复现源码结论。
   保留这一限制，并补充响应体上限与非法路径拒绝；本地 Git provider
   仍用于固定 commit 的读取。
5. 本轮没有对真实 Android 设备执行烧写、删除、远程命令，也没有用真实
   Redmine 数据批量调用模型。没有承诺全站每个按钮、每个像素和所有
   JS/CSS 都已证明无缺陷；现有门禁和新增回归的覆盖范围如上。
6. 未改 GitHub Ruleset、提交或发布远程代码，因此不宣称远程 main CI 已全绿。

## 使用影响

已有晨报及其冻结快照不会被改写。下一次生成或用户主动重新生成晨报时
使用新契约；需要技术根因分析时，在工单详情点击“深度分析此项”。

架构决定见 [ADR 0008](adr/0008-daily-brief-triage-and-diagnosis.md)。
