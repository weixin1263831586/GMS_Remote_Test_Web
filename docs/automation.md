# GMS ATS 运行管理

参考 OmniLab ATS 的运行列表、结果统计和重跑追溯，在现有 GMS 自动化页面中提供以下能力。

## 查看和筛选

进入 **GMS ATS → 追踪与诊断 → 运行监控区域**，可按执行状态、用例结果、Profile ID 和 Worker ID 筛选。
搜索支持项目、分支、设备序列号、Worker、固件路径、运行 ID 和 Gerrit 提交。
筛选先在服务端执行，再按创建时间倒序分页；每页可选 25、50 或 100 条。
“测试中”同时包含启动测试与实际测试运行阶段，“执行失败”包含构建、烧写、测试、分析和上报失败。

**测试报告**页面在服务端先筛选已生成报告的运行，历史报告不会被最近一页无报告的任务挤掉。
两个页面分别记住筛选条件，刷新后恢复；翻页位置不跨刷新保存。
新运行出现后，点击刷新仍保留当前分页边界；返回首页可以看到最新运行。

## 执行状态与用例结果

“完成”表示流水线执行完成，用例结果另行显示：

- **用例通过**：报告提供完整的通过、失败和总数，计数一致、总数大于零，失败数为零。
- **用例失败**：报告中明确存在失败用例，同时展示失败数和总数（可用时）。
- **统计不完整**：报告存在部分计数、计数不一致或总数为零。
- **结果待确认**：历史或结束的运行没有可靠摘要。不会把未知结果显示成通过。

这里的“统计完整”只表示三项计数一致，不保证所有预期模块都已经执行。
摘要在收集报告及完成分析时持久化，不依赖远端执行会话保持在线。
旧记录不会仅凭执行状态补造统计；完整 XML、日志和模块明细仍通过报告入口查看。

## 重跑与追溯

**重跑流水线**使用原配置重新执行整条流水线，包括已配置的构建、烧写和测试。
点击后会说明范围并要求确认。新运行继承原来的所有者、权限快照和 Worker，
保存直接来源运行 ID，但不继承旧的结果、报告或执行租约。
点击来源可查看原运行日志；链路抽屉展示测试配置、重跑来源和用例结果。
仅失败用例重试仍通过原有报告目录重试流程进行。

## 设备占用与完成后的释放

“完成”说明流水线已结束，不保证存在测试报告：仅烧写和 AOA 的运行可跳过测试。
成功收敛时会清理运行自己的预约和 claim；清理失败保留原占用及诊断信息，避免误释放其他任务。

历史已完成 Run 如有遗留预约，在 **追踪与诊断 → 运行监控区域 → 已完成** 筛选后搜索
Run ID，查看卡片的 **释放预约**。创建者或管理员可操作；服务端仍核对预约归属、
租约 generation 和命令/任务状态，无法证明已安全结束时拒绝释放。
取消活跃运行也通过该区域的对应卡片操作。取消计划的未来调度不会自动终止已经启动的 Run。

可用 `#automation?run=<RUN_ID>` 打开指定运行追踪；结果与占用原因以当前状态为准。
权限见 [ADR 0032](architecture/adr/0032-ats-team-read-access.md)，
清理语义见 [ADR 0033](architecture/adr/0033-completed-run-resource-cleanup.md)。

## API

`GET /api/automation/runs` 保留 `status`、`limit`，新增：

| 参数 | 用途 |
| --- | --- |
| `query` | 文本搜索，最多 256 字符，按字面文本匹配 |
| `profile_id` / `worker_id` | 精确筛选，最多 256 字符 |
| `outcome` | `passed`、`failed`、`incomplete`、`unknown` |
| `reports_only` | 仅列出已生成报告的运行 |
| `cursor` | 上一页返回的不透明游标 |

返回 `data.items`、`data.has_more` 和 `data.next_cursor`；翻页时应保持其他筛选参数一致。
记录包含 `test_summary`、`test_type`、`test_suite`、`test_module` 和 `retry_of_run_id`。
列表不返回完整测试计划或大型分析结果。已认证的人类账号可以查看团队所有 Run；
Agent Token 和机器身份仍按原有账号范围读取。取消、重跑和释放预约只允许创建者或管理员操作，
前端以每条记录的 `permissions.can_manage` 显示操作入口。
数据库新增摘要和重跑来源字段，沿用持有 `BEGIN IMMEDIATE` 写锁的幂等迁移。

## 测试计划与自动失败重试

进入 **GMS ATS → 发起**，配置第一套测试后点击 **加入测试计划草稿**，再重复添加下一套。
草稿可上移、下移和移除步骤，最多 20 步；只保存在当前页面内存中，刷新会清空。
每一步保存的是完整配置快照，因此通常第一步构建/烧写，后续步骤选择“仅执行测试”。
后台不会在两个步骤之间自动修改固件或套件配置。

在 **测试计划** 填写名称、执行方式和时区，选择是否启用自动调度后保存：

- 手动：仅点击 **执行一次** 时创建批次。
- 固定间隔：5–10080 分钟；从本次派发/处理时刻计算下次执行。
- 每日 / 每周：使用填写的 IANA 时区和当地时间。夏令时缺失时刻跳过，重复时刻只执行第一次。

可以编辑调度而保留原步骤，或通过新草稿完整替换步骤列表。正在执行的批次继续使用
其原有快照。同一计划有活跃批次时跳过到期周期，服务恢复不补跑所有错过的周期。
自动调度、多步骤推进和自动重试都依赖后台 Automation Worker 运行。

**暂停调度** 只暂停未来定时触发。**停止后续** 阻止当前批次的新步骤和重试，
并取消尚未被 Worker 领取的待执行自动重试；已启动的运行继续。直到当前运行终态，
计划仍保持占用以防重叠。如需终止当前运行，使用**追踪与诊断**中对应运行卡片的取消入口。
失败或未知结果默认停止后续步骤；关闭此选项可以继续，但批次仍保留最终步骤失败事实。

创建运行时可直接设置 **失败用例自动重试上限**（0–5 次，0 为关闭）和
**重试间隔**（10–3600 秒）。该设置也随每个计划步骤保存。自动重试需要：

1. 流水线执行完成，归档摘要明确存在失败用例。
2. 有精确报告 ID、原 Worker 以及真实结果目录；无法确认时记录跳过原因，不猜测目录。
3. 创建者账号仍启用，当前权限和原能力快照均允许执行。

自动重试在同一 Worker、同一套件上使用既有报告目录重试流程，跳过构建和烧写，
不受原模块/用例选择限制；重试轮次、来源链和最早执行时间可在运行监控中查看。
测试执行异常、取消、通过及未知结果均不会触发新重试。
计划等待当前步骤的全部有界重试结束后，再决定是否执行下一步。

计划管理 API 位于 `/api/automation/plans`：创建、更新、设置调度、启停、
执行一次、停止后续和批次历史均按账号隔离，写操作只接受人类会话。
计划修改需要携带当前 `version`；过期修改返回状态冲突并提示刷新。
服务重启后自动完成数据库迁移；无需修改本地运行配置。
架构和权限约束见 [ADR 0020](architecture/adr/0020-scheduled-test-plans-and-bounded-retries.md)。

当前仍使用 GMS 原有执行体系，没有接入 ATS 执行后端。

## 设备准备、分片与预算

**创建运行 → 高级执行设置** 提供以下选项，保存计划时一并保存：

| 选项 | 行为 |
| --- | --- |
| 设备准备 | 保持唤醒、关闭动画、启用 Wi-Fi；按选择顺序执行，可上移/下移 |
| 分片数 | 0 按设备数使用原行为；显式值 1–32，不能超过同一 Worker 的已选设备数 |
| 排队超时 | 等待设备的单次预算，延迟执行前不计时；0 沿用平台设置 |
| 执行超时 | 测试执行阶段预算；0 沿用平台设置 |
| 输出空闲超时 | 仅本次 job/attempt 的 stdout/stderr 长时间无输出时取消；0 关闭此附加限制 |
| 设备条件 | 产品、设备变体、Build ID、Android 版本精确匹配；另支持序列号前缀与板型包含匹配 |

非零超时至少 60 秒。排队/执行最多 7 天，输出空闲最多 1 天。
设备条件同时约束手动选择和自动选择；不会用条件不符的设备补足数量。
分片交给套件自己的 Tradefed 启动器执行，不跨 Worker 拼接结果。

准备动作仅操作已获租约的设备，失败即停止启动测试。总预算 20 秒、单条 ADB 命令
最多 5 秒；Wi-Fi 动作只启用无线开关，连接使用设备已有配置，不保存网络密码。
这里的准备依赖 ADB，不能直接恢复 user build 上已经关闭的 USB 调试。

## 实时模块观测

运行日志详情增加模块/ABI、观察状态、已观察到的通过/失败计数、观察耗时和最近输出，
同时展示准备动作状态。来自不同 attempt 或不同所有者的事件不混合展示。
日志格式无法识别、缺少开始/结束行、历史 Worker 不上报时，观测可能不完整；
观察耗时从收到事件开始计算。最终用例结果仍以归档报告为准，原始日志继续可查。

## 资源与存储

进入 **GMS ATS → 平台 → 资源与存储区域**，选择 Controller 套件文件，显式点击计算 SHA-256，再选择 Worker
预热。已有同 SHA 文件直接命中缓存；下载校验失败不会覆盖原文件。
哈希只描述所选压缩包字节版本，不代表签名认证；解压仍走原有套件管理流程。
大包计算哈希可能需要等待，普通页面刷新只读取目录元数据。

存储策略按账号隔离，默认不自动执行。先设置压缩/删除天数并预览，再手动确认执行；
开启自动策略后由 Automation Worker 每小时处理少量候选。删除天数为 0 表示不删除，
否则必须大于压缩天数。可以将单个 artifact 固定保留，再取消固定。

- 只处理 Controller 已登记的、已结束任务的 stdout.log/stderr.log 副本。
- 报告、XML、测试结果、活动任务和固定保留文件始终跳过。
- 压缩前验证原 SHA；只删除本功能生成的压缩日志，不删除普通原始 artifact。
- 单文件最多 256 MiB；手动每批最多 25 项，自动每账号每小时最多 5 项。
- 预览不返回主机路径；文件变化、过期选择和所有权冲突会拒绝操作。中断由操作日志恢复。

此策略不回收 Worker 原始任务目录和构建服务器文件。

## 计划标签与交换

测试计划支持最多 20 个标签、按标签筛选、选中多项批量暂停或应用当前调度。
批量写入会一次验证所有计划的所有者和版本；任何版本过期则整批失败，刷新后重试。

导出 JSON 保留可重用步骤和调度，移除授权快照、密码/Token 等敏感字段以及 URL 凭据和
查询参数。导入创建新计划并强制暂停，需重新补齐外部凭据并明确启用。导入不会立即运行。

## 升级和边界

高级执行、观测和缓存能力需要 Controller、Automation Worker 与目标 Worker 使用兼容实现。
目标 Worker 重新注册后应声明 `execution_options_v1`、`module_progress_v1` 和
`suite_cache_sha256_v1`；旧 Worker 的高级选项和 SHA 固定预热会返回明确冲突。
仅重启 Web 服务不能更新远程 Worker。Agent 部署验收仍使用 `gms-agent doctor --json`
及 `gms-rt-system-selfcheck --json` 的既有路径。

架构约束见 [ADR 0021](architecture/adr/0021-ats-execution-options-and-evidence-retention.md)。
刷机后的 AOA 恢复与后续验证流程见 [AOA 架构](aoa-mechanism-and-architecture.md)，
具体回放、认证和模板操作见 [AOA 用户指南](aoa/user-guide.md)。
